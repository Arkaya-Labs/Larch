# m13 against llama.cpp on a 16 GB GPU: release build, 26 Nov 2026

Larch's release build against llama.cpp on the same machine, at W4 with 1, 4, 8 and 16 concurrent chats, on
m13 (`bench/models.toml`: a 35B-A3B hybrid MoE, Q3_K_M, 17.1 GB) as published and on larch's faster copy of
it (`larch faster`, #6).

Test machine: RTX 5070 Ti 16 GB, Ryzen 7 9800X3D, Windows 11 + WSL2 (8 logical CPUs in WSL). llama.cpp
b12723 (`abca692`), `-ngl 99 -fa on -ctk f16 -ctv f16 -t 8 -b 2048 -ub 1024`, with `--n-cpu-moe` as each
row says. Raw results: [`35b-final-2026-11-26/`](35b-final-2026-11-26/).

## Summary

1. **W4@1, original file: larch ahead.** 130.4 tok/s against 119.8 for llama.cpp `--n-cpu-moe 4`
   (+8.8 %), and +8.6 % on the clean pair (135.4 against 124.7). The second pair of runs was slowed on both
   sides by other use of the PC (Protocol notes). TTFT p50 is 27 % lower and TPOT p99 23 % lower (noise under
   the disturbed runs' spread). TTFT p99 is 20 % higher: llama.cpp's 1,024-token ubatches read a long prompt
   in fewer steps.
2. **W4@4, original file: level on throughput, ahead on latency.** 245.6 against 243.0 tok/s (+1.1 %,
   noise). TTFT p50 is 38 % lower, TTFT p99 54 % lower and TPOT p99 5 % lower (noise). At its run flags,
   llama.cpp's `--n-cpu-moe 4` already exceeds the free memory it reports here by an estimated ~245 MiB.
3. **W4@8: larch behind.** 186.6 against 287.1 tok/s (−35 %, one run a side). Cause: at 4.3 s into the run
   the engine's seat switch reloaded the model onto its many-chats plan (Why W4@8 drops). That plan keeps no
   prompt-streaming pool. So steps that mix a prompt chunk with 5 decode rows ran their host experts on the
   CPU (472 ms each, 69 s of a 345 s run), and 6-row decode steps ran without decode graphs (25.7 ms against
   13.8 ms for a replayed 4-row step, 130 s). llama.cpp runs 8 sequences ~700 MiB past its reported free
   memory.
4. **W4@16: larch ahead.** 186.3 against 74.0 tok/s (+152 %, one run a side), after the same switch. llama.cpp's
   `--n-cpu-moe 4` is ~1.6 GB past its reported free memory there (TPOT p99 242 ms). Larch serves 6 seats and
   queues the rest (TTFT p99 27.6 s against 26.4 s).
5. **Hand-set, spills on Windows/WSL: larch `LARCH_CPU_EXPERT_LAYERS=3` against llama.cpp `--n-cpu-moe 3`:
   larch behind.** W4@1 92.9 against 131.6 tok/s (larch r1 disturbed; r2 120.0, −9 %) and W4@4 161.1 against
   259.2 (−38 %). Larch's post-load check accepts the load. Within the reported free memory it then keeps
   neither the prompt-streaming pool nor four state slots (it keeps two), so its TTFT is 4.6 s at p50 at W4@4. Its decode is
   ahead (TPOT p99 6.58 against 7.57 ms at W4@1).
6. **Faster copy.** llama.cpp refuses this file at load (its experts are split into tensors only larch reads),
   so its rows are compared with llama.cpp on the original file. W4@1: 163.0 tok/s (one run) against 119.8, **+36 %** (TTFT p50 112 ms, TPOT p99 5.72 ms). Its W4@4, @8 and @16 rows were cut for time; the 26 Nov morning report has W4@4 at 317.6 tok/s on the build before today's changes.
7. **What changed today** (same-session A B B A against the build before each step):
   - Two CPUs left to the engine and the GPU driver beside a GPU: W4@1 +4.6 %.
   - Fused CPU gate and up, plus prompt streaming from page-locked memory: W4@1 +6.2 % and W4@4 +10.7 %, with
     lower TTFT and TPOT p99 at both loads.
   - Overlapping the host-expert CPU work with GPU work, and 256-token chunks beside replying chats, were
     dropped (Steps).
8. **Parity:** `larch parity` on the release build (`7bdb1fe`, `build.txt`) against the m13 llama.cpp dump: prefill
   passes (mean KL 0.0041, decisive top-1 1.000, 100 prompts) and decode passes (mean KL 0.0040, decisive top-1
   1.000, 56,529 graph-replayed steps, none eager), under the dump's bound of 0.0354 (`parity-m13-*.log`).

## Why W4@8 drops: a mid-run switch to the many-chats plan

Each larch run's `LARCH_FIT_DIAGNOSTICS` lines (`larch_host_experts_load`: host layers, free bytes, bytes needed,
state slots; `larch_stream_pool`: wanted, granted, pool on):

| Run | Load at start | During the run |
|---|---|---|
| W4@1 r1, W4@4 r1 and r2 | 4 host layers, 4 state slots, stream pool on | no switch |
| W4@1 r2 | short at first (482 against 637 MB free: another program held VRAM during the disturbed window), so 5 host layers and 5 slots, pool on | no switch |
| **W4@8 and W4@16** | 4 host layers, 4 slots, pool on | **seat switch at 4.3 s and 4.0 s (`larch_seat_switch,4`): a reload onto the many-chats plan.** That plan's static per-expert placement needs a route histogram, and the bench moves those aside before each run, so it fell back to whole layers: **4 host layers, 6 slots (7 refused), stream pool off (`larch_stream_pool,184549376,0,false`)** |
| hand-set `LARCH_CPU_EXPERT_LAYERS=3`, W4@1 and @4 | 3 host layers, 2 slots (4 refused), pool off | no switch |

In the loader (`crates/larch-engine/src/lib.rs`), a load asked for `MANY_SEATS` or more seats on CUDA selects
the expert-cache plan (`cache = Some(false)`, static residency). The prompt-streaming pool is planned only when
`cache.is_none()`, so that plan, and its fall-back to whole layers, carries no pool. Above 4 chats the switch
therefore trades the pool (prompt chunks 130 ms, against 472 ms without it) for two more seats.

## Next fixes, from the profile

1. **Stay on the whole-layer 4-seat plan above 4 chats**, keeping the stream pool. At the least, plan the pool
   on the whole-layer fall-back when the per-expert placement has no histogram. Expected: W4@8 near W4@4's
   245 tok/s, with chats past the fourth queued.
2. Then decode graphs for the 5- and 6-row buckets where seats exceed 4 (6-row steps ran eager at 25.7 ms).
3. W4@1 TTFT p99 (+20 % against llama.cpp): long prompts still take 512-token streamed steps, where llama.cpp
   reads 1,024 per ubatch.

## Protocol notes

- **What "fits" means here.** llama.cpp reports 15,009 MiB free on this card at every load; larch reads the same
  figure and never plans past it. The probe lines (`wsl5070-m13-llama-load.txt`, redacted to the free-memory and
  CUDA0 buffer lines) were taken with one sequence. The served W4@c rows keep c sequences, and llama.cpp's
  recurrent state grows by 62.8 MiB per sequence (251.3 MiB at 4 in the 26 Nov load). So with this report's
  flags (`-ub 1024`, a 1,010 MiB compute buffer), the estimated CUDA0 totals are:

  | `--n-cpu-moe` | W4@1 | W4@4 | W4@8 | W4@16 |
  |---|---|---|---|---|
  | 4 | 14,916 MiB (fits) | ~15,254 | ~15,705 | ~16,608 |
  | 3 | 15,280 | ~15,618 | ~16,069 | ~16,972 |

  Every cell past 15,009 MiB runs partly from shared system memory through the Windows driver's fallback.
  The 26 Nov report's "ncm 4 fits (14,750 MiB)" came from the search probe at default `-b/-ub`, with a smaller
  compute buffer; at the flags the rows run with, ncm 4 fits at W4@1 only.
- **The faster copy and llama.cpp.** The copy splits each layer's experts into `ffn_*_exps` (the experts kept
  at Q3_K/Q4_K) and `ffn_*_cold_exps` (Q2_K) with a lookup table only larch reads. llama.cpp refuses it at load:
  `check_tensor_dims: tensor 'blk.0.ffn_down_exps.weight' has wrong shape; expected 512, 2048, 256, got 512,
  2048, 167, 1` (`copy-load.log`). So its rows are compared with llama.cpp on the original file.
- **The hand-set pair.** `LARCH_CPU_EXPERT_LAYERS=3` passes larch's post-load check. Within the reported free
  memory, though, its plan keeps neither the 184.5 MB prompt-streaming pool (`larch_stream_pool,184549376,0,false`)
  nor four state slots (two slots: 201 against 330 MB of recurrent state). Prompts beside a host layer then prefill on the
  CPU, and at W4@4 a chat waits for a seat. llama.cpp's `--n-cpu-moe 3` covers the same shortfall from shared
  system memory.
- **Disturbed runs.** Between 16:09 and 16:29 local time, other use of the PC slowed both engines' second W4@1
  runs: TPOT p99 rose from 8.01 to 11.39 ms for llama.cpp and from 6.93 to 8.01 ms for larch, and larch's run
  took 514 against 476 s. That larch run also loaded while another program held ~190 MB of VRAM, so it planned
  five host layers instead of four (Why W4@8 drops). The hand-set larch W4@1 r1 (65.7 tok/s, 981 s against 537 s for r2) ran in a second
  such window. All of them stay in the tables, and the run spreads carry them into the noise rule.
- **Cut for time.** The faster copy's second runs at W4@1 and W4@4, and its W4@8 and W4@16 rows, were skipped to
  keep the GPU work inside the evening's limit.
- **Statistics.** Each cell is the mean of its runs; spread = (max − min) / mean. A margin is noise when under
  2 % or under either side's spread; a one-run cell has only the 2 % rule.
- `compare.log`: `scripts/baseline.py compare` on every llama.cpp × larch pair of the original file at W4@1 and @4.
- Result files keep every field except each request's `token_gaps_ms`.
