# Lane Z: the GPU reads the host experts in place at decode, 27 Nov 2026: not kept

Test machine: RTX 5070 Ti 16 GB (PCIe 5.0), Ryzen 7 9800X3D, Windows 11 + WSL2 (8 logical CPUs in WSL). Model m13
(`bench/models.toml`), the original file. Branch `perf/35b-zero-copy`. It is the kept stack of `perf/35b-all-chats`
(`ef28629`) plus Lane Z (`2b90422`). The night's report is `bench/results/35b-all-chats-2026-11-27.md` on
`perf/35b-all-chats`.

## What Z is

Today the host layers' routed experts run on the CPU at decode, with a device round trip per host layer. Each such
layer also ends a graph piece. Z keeps those experts where they already are, in page-locked host memory (#15), and lets
the GPU's own kernels read them in place over PCIe for decode rows: `routed()` on the compute stream, captured in the
step's graph, with no round trip and no CPU part. Prefill rows still stream through the pool.

- `kernels/src/cuda/backend.cu`: `larch_buffer_wrap_host` wraps a range inside a page-locked host buffer
  (`pinned_holds`) as a device buffer at `cudaHostGetDevicePointer`'s address. Freeing it never calls `cudaFree`. Any
  other memory, a file map included, stays UNSUPPORTED. This is the one header change approved for the night: the
  comment in `kernels/include/larch.h`.
- `larch-kernels`: `Buffer::view_host`, a read-only view over a range of a host buffer. It keeps that buffer alive.
- `transformer.rs`: at load, host layers whose experts are page-locked get a device view (after `share_host`, so the
  pool keeps its copy source). `moe_ffn` runs a host layer's decode rows from the view. Check steps, adapters, router
  deltas, a recording or split load, a mixed layer and the MTP block keep the CPU path. A diagnostics line names the
  mapped layers and bytes.

## Tests (all pass; each one's RED was watched)

- `ctest wrap_host` (CUDA):
  - `mmvq_id` over a wrapped range of Q4_K and Q8_0 experts writes the device copy's bytes;
  - a malloc'd pointer and a range one byte past the host buffer are UNSUPPORTED;
  - the host buffer is whole after the wrap is freed.
  - RED: with the wrap UNSUPPORTED, the wrap call fails.
- `larch-kernels` `view_host_checks_before_ffi` (CPU): an empty range, a range past the end, a buffer that is not a host
  buffer and another device's host buffer are refused before the backend. RED: without the checks, all four reach it.
- `larch-kernels` `a_host_view_on_cuda_reads_the_host_bytes` (CUDA): a view reads the host bytes back in place, outlives
  its host buffer's handle, and refuses uploads.
- `larch-model` `mapped_host_layers_decode_as_resident_layers_do` (CUDA): decoding through 1 or 2 mapped host layers
  gives the resident load's logits **bit for bit**. RED: with the decode-row path off (the CPU path), 1 host layer
  differs.
- Parity on m13 (prefill and decode, Z's build): see "Parity" below.

## Z0: the bus, measured (a standalone nvcc test, not in the repo)

1.6 GB of `cudaHostAlloc` memory, as larch allocates it; its device pointer equals the host pointer (UVA). A coalesced
16-byte-load read kernel ran on all 70 SMs, 50 reps, each over a fresh window so the 48 MB L2 holds nothing:

| Size | Kernel reads host memory in place | The same from device memory | `cudaMemcpyAsync` from it | CPU, 6 threads |
|---|---|---|---|---|
| 12 MB | 52.9 GB/s | 676.0 | 57.5 | 23.8 (thread start-up included) |
| 42 MB | 53.2 | 797.0 | 57.7 | 50.2 |
| 64 MB | 53.5 | 817.4 | 57.7 | 55.6 |

The GO rule was 45 GB/s or more at 12 and 42 MB, so Z0 said GO. It predicted about 0.22 ms per host layer at 1 row
(11.9 MB), against 0.41 ms on the CPU.

## Z2: what the decode kernels actually read

**Per host layer**: `larch_mmvq_id` for gate and up (Q3_K `[256*512, 2048]`) and down (Q4_K `[256*2048, 512]`), m13's
shapes, over a wrapped page-locked layer and over device memory. 200 reps, each with other experts:

| Rows | Mapped host memory | GB/s, by (row, slot) pairs' bytes | GB/s, by unique experts' bytes | Device memory |
|---|---|---|---|---|
| 1 (8 pairs, 11.9 MB) | **1.297 ms** | 9.2 | 9.2 | 0.082 ms |
| 4 (32 pairs, 47.7 MB; 45.6 MB unique) | **4.649 ms** | 10.3 | 9.8 | 0.227 ms |

The decode kernels read the bus at **9 to 10 GB/s, not 53**. Z0's kernel filled the GPU with long coalesced streams. A
decode `mmvq_id` launch is a few blocks per expert matrix, so over the bus it is bound by latency, not bandwidth. A
shared expert does cross PCIe once per pair (47.7 against 45.6 MB at 4 rows), but that is a small part of it.

## Verdict

**Not kept.** The keep rule needed a win outside noise at W4@1, no loss at W4@4, and TTFT p99 and TPOT p99 within 3 %.
Z loses 30 % at W4@1 and 46 % at W4@4. It is not a bug in the wiring: the bits match a resident load exactly, and the
end-to-end loss (+4.7 ms a step at 4 rows across 4 layers) matches the kernels' own read rate over the bus. The night
finished on `perf/35b-all-chats` without Z.

## Next step

Make the decode read stream, not chase, over the bus. Read the routed experts' bytes into device memory with one
gather-copy kernel per layer, sized like Z0's (all SMs, 16-byte coalesced loads, about 53 GB/s), inside the graph, and
then run `mmvq_id` from that copy with the ids remapped. Expected per host layer: about 0.24 ms at 1 row (11.9 MB) and
about 0.9 ms at 4 rows (unique experts only), against 0.41 and 1.2 ms on the CPU. The gather needs a new kernel entry
point in `kernels/include/larch.h` (an expert gather by ids, or a copy with device-side offsets), which needs human
approval. A per-pair `mmvq_id` variant with more loads in flight (`cp.async`) is the alternative inside the backend, with
no header change, but tonight's numbers say latency, not bytes, is the limit.
