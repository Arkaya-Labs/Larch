# Repository guidance for coding assistants

Read the task, the relevant source and the applicable sections of
[larch-architecture.md](larch-architecture.md) before changing behavior. Follow
[CONTRIBUTING.md](CONTRIBUTING.md) for the contribution flow and current dependency/CI limitations.

- Make focused changes and reuse existing helpers, types and platform facilities. Trace callers to fix
  a shared root cause; avoid duplicate implementations, speculative scaffolding and new abstractions
  without a concrete need. Explain new dependencies in the PR.
- `unsafe` is allowed only in `larch-sys` and `larch-kernels`. Every unsafe block needs a `// SAFETY:`
  comment explaining the invariant. Preserve host-side shape/dtype validation and bounds checks at all
  trust boundaries, including every GGUF length, count and offset.
- Shared contract changes in `crates/larch-records/**` or `kernels/include/larch.h` require human
  approval. Read all affected consumers and explain compatibility implications before changing them.
- Preserve error handling and durable transcript/journal/ring-flush behavior. Do not swallow errors,
  remove recovery paths or discard data to simplify a change. Document public items and explain
  non-obvious constraints and the trigger for revisiting an intentional limitation.
- Check kernels against the CPU reference and models against llama.cpp using the same GGUF. Never
  weaken tests or numerical tolerances, or substitute another assistant's implementation as the oracle.
  Keep meaningful regression coverage for non-trivial logic.
- Run checks appropriate to the change in CONTRIBUTING.md. Rust changes need formatting, clippy and
  tests; kernel changes also need ctest; kernel/model changes need small-model parity, and tokenizer
  changes need tokcheck. Report exact commands and outcomes. Skipped, unavailable or queued is not passed.
- Hot-path changes need comparable measurements and `scripts/bench-merge` as applicable. Revert a loss
  greater than 3% unless it is a correctness fix; explain the exception and measured cost.
- Target `dev` and obtain human review before merge. Never replace a missing component with a fake to
  get a check to pass.
- Keep model identifiers in `bench/models.toml`; use aliases in code, commits and PR text. Never commit
  model weights, credentials or personal information. Never put personal information in outbound
  requests, including User-Agent headers. Redact logs and reproductions; use the private reporting route
  in [SECURITY.md](SECURITY.md) for vulnerabilities when it is established.

## Commits and pull requests

- Commit with the GitHub noreply address of the person you work for
  (`<id>+<login>@users.noreply.github.com`), as author and committer. Check `git config user.name`
  and `git config user.email` before the first commit. Never put a personal email address in a
  commit, a file or a PR.
- Say that AI assisted, and never claim it wrote the change: end a commit message with the trailer
  `Assisted-by: Claude Code` (or the tool used) and a PR description with `Assisted by Claude Code`.
  No `Co-Authored-By` lines naming an assistant and no session links. In PR comments and reviews,
  add no "Assisted by" line: the tool's own "Generated by" footer, where it adds one, is the
  disclosure there.
- Never rewrite pushed history: no force push, and no rebase or amend of a commit that is already
  pushed. Start each change on a new topic branch from the current target branch; pull requests are
  squash-merged.

Reports and PR descriptions should state what changed, why, the exact validation and remaining blockers.
Do not claim a build, hardware result, release qualification or security control without evidence.
